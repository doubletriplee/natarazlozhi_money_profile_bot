# Архитектура MVP

```text
Telegram long polling
        │
        ├── первое изображение → согласие → кнопочный выбор даты и времени → город
        ├── GeoNames → Swiss Ephemeris → правила → зашифрованный результат
        ├── бесплатная карточка → кнопка «Узнать силу» или предложение через час
        ├── fake-подтверждение без списания → изображение + текст аватара + профессии
        └── кнопка после результата или через час → предложение ручного полного разбора

Caddy → 127.0.0.1:18080 → aiohttp (/, /healthz, /privacy, /consent, /terms, /source)
SQLite WAL: пользователи, согласия, профили и события
```

Маршрут `/` отдаёт лёгкую адаптивную страницу магазина без форм и клиентских библиотек. Кнопки
услуг ведут в публичный Telegram-бот, указанный в реквизитах финального текста Публичной оферты;
оттуда же footer получает данные исполнителя. Поэтому runtime-username закрытого staging-бота не
попадает на публичную витрину и второй набор юридических данных не поддерживается. В тестовом и
staging-режимах главная прямо сообщает, что списание денег и покупка не происходят.

Имя, возрастное подтверждение, PDF и шкала оценки в текущем пользовательском сценарии не
используются. Email не собирается в публичном fake-режиме; закрытый staging запрашивает его только
для создания тестового счёта Robokassa. Команда `/profile` повторно отправляет бесплатный сценарий
до покупки или сохранённый платный результат после неё. Если текст платного результата превышает
лимит подписи Telegram, бот переносит последний цельный блок в следующее сообщение без сокращений.
Username продавца берётся из единой настройки `SUPPORT_USERNAME`; ссылка кодирует готовый текст
сообщения.

Кнопка с ценовым ориентиром 149₽ работает в публичном fake-режиме и явно сообщает, что деньги не
списываются. Реальная автоматическая оплата сначала проходит через закрытый `APP_ENV=pilot`.
Целевая платёжная архитектура production предусматривает только Robokassa. Telegram Stars не
используются, не планируются и не должны добавляться как альтернативный или резервный провайдер.
Автоматическая выдача оплаченного цифрового результата остаётся внутри того же бота. Владелец
осознанно принял связанный с этой схемой известный риск ограничения или удаления бота; архитектура
не заявляется соответствующей правилам Telegram.

В закрытом `APP_ENV=staging` используется тестовая Robokassa без списаний. Доступ разрешён только
Telegram ID из `TEST_ACCESS_TELEGRAM_IDS`. После нажатия кнопки бот запрашивает email, создаёт
одноразовый счёт на 24 часа и отправляет URL платёжной страницы. Robokassa отправляет единственное
серверное уведомление на `ResultURL`, заданный в технических настройках магазина. Приложение
проверяет его подпись паролем №2, сумму и номер заказа, отвечает `OK{InvId}`, а повторное уведомление
обрабатывает идемпотентно. Дополнительный `ResultURL2` не используется: это отдельный JWS-канал,
который не нужен для обычной одноразовой оплаты. Success-переадресация никогда не подтверждает
платёж и только возвращает пользователя в Telegram. В журнале фиксируются факт получения,
результат безопасной проверки и признак первой обработки без номера счёта, email, подписи или тела
запроса. Staging, pilot и production должны использовать разные токены бота, базы и ключи шифрования.
Параллельные запросы создания счёта сериализуются и переиспользуют один активный invoice.
Email и временные ссылки оплаченного, неоплаченного или неудачного заказа очищаются по
`PAYMENT_CONTACT_RETENTION_DAYS`; при ошибке создания счёта email удаляется сразу. Тестовый журнал
после этого срока удаляется целиком. Для реальной оплаты сохраняется минимальная запись без email,
платёжной ссылки и обратимого идентификатора операции. `PAYMENT_RECORD_RETENTION_YEARS` не может
быть меньше пяти лет. После `/delete_my_data` связь с Telegram и результатом уничтожается, а
просроченный платёжный журнал удаляется; незавершённый или неопределённый возврат сохраняется до
ручной сверки. Сохранённая запись не запускает доставку по удалённому профилю.

Код подтверждения возврата потребляется атомарно до обращения к Robokassa, поэтому два
одновременных административных запроса не могут отправить два возврата. Платёж проходит внутренние
состояния проверки и отправки запроса. Если соединение оборвалось после возможной передачи запроса
Robokassa, платёж получает состояние `uncertain`: новый код не выдаётся, пока оператор вручную не
сверит операцию в кабинете провайдера. Явно отклонённый запрос можно подготовить повторно. Ошибка
проверки статуса одного возврата не прерывает обновление остальных.

Все ответы API Robokassa ограничены 64 КиБ до разбора. XML проверки операции обрабатывается
защищённым парсером с запретом DTD и сущностей; некорректный, чрезмерно большой или потенциально
опасный ответ считается неопределённой транспортной ошибкой и не подтверждает платёж или возврат.

Фоновый обработчик сначала выбирает ограниченную пачку оплаченных заказов, затем небольшие пачки
напоминаний и предложений. Это не даёт рекламным и сервисным сообщениям задерживать уже оплаченный
результат. Обработчик отмечает heartbeat; `/healthz` проверяет и базу, и доставку. После трёх
последовательных сбоев цикла процесс завершается, чтобы политика перезапуска контейнера подняла
чистый экземпляр.

Тяжёлый расчёт защищён локальным шлюзом: одновременно выполняются не более двух вычислений, общая
очередь ограничена шестнадцатью пользователями, а повторное нажатие того же пользователя не создаёт
второй профиль. Состояние ожидания не сохраняется в SQLite, поэтому перезапуск не оставляет анкету
навсегда заблокированной и позволяет повторить расчёт.

Отдельный контейнер `backup` каждые `BACKUP_INTERVAL_HOURS` создаёт согласованный online-snapshot
SQLite, шифрует его AES-256-GCM и сразу пробует расшифровать во временную память. Копия считается
успешной только после `PRAGMA integrity_check=ok`; запись файла и обезличенного `status.json`
атомарна. Приложение включает свежесть этого статуса в `/healthz`, поэтому отсутствие проверяемой
копии дольше `BACKUP_MAX_AGE_HOURS` видно штатному deploy и доступно внешнему монитору. Локальные копии
хранятся 14 дней. 3 сентября 2026 года владелец решил не создавать вторую копию и явно принял риск
одновременной потери рабочей БД и архива при отказе основного сервера. Существующий мониторинг на
немецком сервере используется только для технических статусов и Telegram-оповещений; копии и
персональные данные туда не передаются.

В `APP_ENV=pilot` используются основные пароли Robokassa и `ROBOKASSA_TEST_MODE=false`, но весь
Telegram-интерфейс доступен только ID из `PILOT_ACCESS_TELEGRAM_IDS`. Создание боевого invoice
дополнительно защищено независимыми `LIVE_PAYMENTS_ENABLED` и
`PILOT_LIVE_PAYMENT_REVIEWED`. Первичная настройка всегда ставит `false`, поэтому загрузка боевых
секретов не включает списания. Штатный deploy принимает `true` только для одного ID, совпадающего с
единственным admin ID, и только после привязанного к точному commit запроса. При неуспешном обновлении
закрытого live-pilot откат выключает новые счета. ResultURL, доставка уже подтверждённых заказов и
административный возврат не зависят от этого выключателя. Публичный `APP_ENV=production` остаётся
отдельной стадией после закрытого полного цикла.

Для фискализации Invoice API получает email и одну позицию фактической услуги с количеством, суммой,
НДС, способом и предметом расчёта. API возврата также всегда получает `InvoiceItems`, поскольку без
состава Robokassa выполняет только возврат средств без возвратного фискального чека. Подключённые и
одобренные ФНС «Робочеки СМЗ» формируют документы на стороне Robokassa; приложение не обращается к
ФНС напрямую.

Персональные значения шифруются AES-256-GCM с отдельным контекстом каждого поля. Telegram ID ищется
по HMAC-SHA256 и не хранится открыто. Приложение не сохраняет полные Telegram updates и callback-тела.
Если `ADMIN_TELEGRAM_IDS` задан, только этот список определяет административный доступ; устаревшая
bootstrap-запись в базе не расширяет права. Хранимая HMAC-запись используется лишь в локальной
test/development-конфигурации без заданного списка.
Административная статистика считает количество подтверждённых оплат исторически, но показатель
выручки показывает чистую сумму: полностью завершённые возвраты из неё исключаются.

Методика, правила и факты карты версионируются отдельно. Сохранённый профиль не пересчитывается
при обновлении движка.
