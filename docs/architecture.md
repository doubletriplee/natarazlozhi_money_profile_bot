# Архитектура MVP

```text
Telegram long polling
        │
        ├── первое изображение → согласие → кнопочный выбор даты и времени → город
        ├── GeoNames → Swiss Ephemeris → правила → зашифрованный результат
        ├── бесплатная карточка → кнопка «Узнать силу» или предложение через час
        ├── fake-подтверждение без списания → изображение + текст аватара + профессии
        └── кнопка после результата или через час → предложение ручного полного разбора

Caddy → 127.0.0.1:18080 → aiohttp (/, /healthz, /privacy, /consent, /terms, /source)
SQLite WAL: пользователи, согласия, профили и события
```

Маршрут `/` отдаёт лёгкую адаптивную страницу магазина без форм и клиентских библиотек. Кнопки
услуг ведут в публичный Telegram-бот, указанный в реквизитах финального текста Публичной оферты;
оттуда же footer получает данные исполнителя. Поэтому runtime-username закрытого staging-бота не
попадает на публичную витрину и второй набор юридических данных не поддерживается. В тестовом и
staging-режимах главная прямо сообщает, что списание денег и покупка не происходят.

Имя, возрастное подтверждение, PDF и шкала оценки в текущем пользовательском сценарии не
используются. Email не собирается в публичном fake-режиме; закрытый staging запрашивает его только
для создания тестового счёта Robokassa. Команда `/profile` повторно отправляет бесплатный сценарий
до покупки или сохранённый платный результат после неё. Если текст платного результата превышает
лимит подписи Telegram, бот переносит последний цельный блок в следующее сообщение без сокращений.
Username продавца берётся из единой настройки `SUPPORT_USERNAME`; ссылка кодирует готовый текст
сообщения.

Кнопка с ценовым ориентиром 149₽ работает в публичном fake-режиме и явно сообщает, что деньги не
списываются. Реальная автоматическая оплата сначала проходит через закрытый `APP_ENV=pilot`.
Целевая платёжная архитектура production предусматривает только Robokassa. Telegram Stars не
используются, не планируются и не должны добавляться как альтернативный или резервный провайдер.
Автоматическая выдача оплаченного цифрового результата остаётся внутри того же бота. Владелец
осознанно принял связанный с этой схемой известный риск ограничения или удаления бота; архитектура
не заявляется соответствующей правилам Telegram.

В закрытом `APP_ENV=staging` используется тестовая Robokassa без списаний. Доступ разрешён только
Telegram ID из `TEST_ACCESS_TELEGRAM_IDS`. После нажатия кнопки бот запрашивает email, создаёт
одноразовый счёт на 24 часа и отправляет URL платёжной страницы. Robokassa отправляет единственное
серверное уведомление на `ResultURL`, заданный в технических настройках магазина. Приложение
проверяет его подпись паролем №2, сумму и номер заказа, отвечает `OK{InvId}`, а повторное уведомление
обрабатывает идемпотентно. Дополнительный `ResultURL2` не используется: это отдельный JWS-канал,
который не нужен для обычной одноразовой оплаты. Success-переадресация никогда не подтверждает
платёж и только возвращает пользователя в Telegram. В журнале фиксируются факт получения,
результат безопасной проверки и признак первой обработки без номера счёта, email, подписи или тела
запроса. Staging, pilot и production должны использовать разные токены бота, базы и ключи шифрования.
Параллельные запросы создания счёта сериализуются и переиспользуют один активный invoice.
Email в неоплаченном или неудачном заказе очищается по `PAYMENT_RETENTION_DAYS`; при ошибке создания
счёта он удаляется из заказа сразу. После `/delete_my_data` сохранённый минимальный платёжный журнал
не запускает отложенную доставку по удалённому профилю.

В `APP_ENV=pilot` используются основные пароли Robokassa и `ROBOKASSA_TEST_MODE=false`, но весь
Telegram-интерфейс доступен только ID из `PILOT_ACCESS_TELEGRAM_IDS`. Создание боевого invoice
дополнительно защищено независимым `LIVE_PAYMENTS_ENABLED`. Первичная настройка и штатный deploy
пока требуют значение `false`, поэтому загрузка боевых секретов не включает списания. ResultURL,
доставка уже подтверждённых заказов и административный возврат не зависят от этого выключателя.
Публичный `APP_ENV=production` остаётся отдельной стадией после закрытого полного цикла.

Персональные значения шифруются AES-256-GCM с отдельным контекстом каждого поля. Telegram ID ищется
по HMAC-SHA256 и не хранится открыто. Приложение не сохраняет полные Telegram updates и callback-тела.

Методика, правила и факты карты версионируются отдельно. Сохранённый профиль не пересчитывается
при обновлении движка.
