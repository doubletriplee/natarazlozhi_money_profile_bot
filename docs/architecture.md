# Архитектура MVP

```text
Telegram long polling
        │
        ├── анкета → GeoNames → Swiss Ephemeris → правила → зашифрованный результат
        │
        ├── кнопка оплаты → Robokassa Invoice API → внешняя платёжная страница
        │                                              │
        │                           подписанный ResultURL
        │                                              ▼
        └──────────────────────────── очередь доставки → PDF из 6 блоков
                                                       → через 3 минуты допредложение

Caddy → 127.0.0.1:18080 → aiohttp (/healthz, /privacy, /terms, /source, callbacks)
SQLite WAL: пользователи, согласия, профили, заказы, платежи, события, доставка
```

Доставка разрешается только после проверки подписи `ResultURL`, точного `InvId` и суммы.
`SuccessURL` используется исключительно как информационная страница. Повторный callback не создаёт
второй платёж или очередь. Очередь обеспечивает доставку после рестарта; Telegram не предоставляет
идемпотентный ключ для `sendDocument`, поэтому в узком окне между отправкой PDF и записью message ID
возможна повторная отправка документа. Отложенное допредложение хранит время выдачи в БД,
переживает рестарт и не блокирует статус доставленного профиля. Остальные повторные события
подавляются на уровне БД.

Персональные значения шифруются AES-256-GCM с отдельным контекстом каждого поля. Telegram ID ищется
по HMAC-SHA256 и не хранится открыто. Приложение не сохраняет полные Telegram updates и callback-тела.

Методика, правила, факты карты и тексты версионируются отдельно. Сохранённый оплаченный профиль не
пересчитывается при обновлении движка.
