# Развёртывание и откат

Целевой каталог: `/opt/natarazlozhi_money_profile_bot`. Контейнер работает от UID/GID 10001,
с read-only root filesystem, без Linux capabilities, с лимитом 0,5 CPU и 768 МБ RAM. Временная
память 256 МБ позволяет проверять восстановление растущей SQLite без записи расшифрованного файла
на постоянный диск. HTTP опубликован только на `127.0.0.1:18080`.

Само приложение добавляет CSP, HSTS, `X-Frame-Options`, `nosniff`, Referrer-Policy,
Permissions-Policy и Cross-Origin-Opener-Policy к обычным ответам, управляемым HTTP-ошибкам и
перенаправлениям. Caddy остаётся единственной публичной точкой входа и передаёт фактический адрес
клиента для встроенного ограничителя частоты; напрямую публиковать порт приложения нельзя.

## Публичный тест без оплаты

1. Скопировать `compose.yaml`, создать `runtime/data`, положить GeoNames DB в
   `runtime/data/cities.sqlite3` и дать каталог UID 10001.
2. Создать `.env` с правами `600` на основе `.env.test.example` и обязательно установить
   `APP_ENV=test`, `PAYMENT_MODE=fake`, `PAYMENT_CONTACT_RETENTION_DAYS=30` и
   `PAYMENT_RECORD_RETENTION_YEARS=5`. Бот доступен всем пользователям.
3. Установить Caddy-файл из `deploy/` в существующий `sites-enabled`, выполнить `caddy validate`.
4. Запустить образ по точному commit SHA из GHCR и проверить главную `/`, `/healthz`, `/privacy`,
   `/consent`, `/terms`, `/source`, а также переходы с главной в Telegram-бот и на три юридические
   страницы.
5. Проверить, что интерфейс сообщает об отсутствии списания, а платёжные callback URL недоступны
   для пользовательского сценария.

Реальную оплату в этой конфигурации включать нельзя. Публичный production разворачивается только
после выполнения [отдельных релизных блокировок](./release-gates.md).
После их выполнения единственным целевым провайдером реальной оплаты остаётся Robokassa. Telegram
Stars не используются и не рассматриваются как запасной способ оплаты. Владелец осознанно принял
известный риск ограничения или удаления бота из-за несоответствия этой схемы правилам Telegram;
принятие риска не означает соответствие и не отменяет остальные блокировки релиза.

## Закрытый staging Robokassa

Для проверки платёжного пути без списаний используется отдельная конфигурация на основе
`.env.staging.example`:

- `APP_ENV=staging`;
- `PAYMENT_MODE=robokassa`;
- `ROBOKASSA_TEST_MODE=true`;
- заполненные `ROBOKASSA_MERCHANT_LOGIN`, тестовые пароли №1/№2;
- непустые `ADMIN_TELEGRAM_IDS` и `TEST_ACCESS_TELEGRAM_IDS`;
- три отдельные случайные ключа шифрования;
- `PAYMENT_CONTACT_RETENTION_DAYS=30` и `PAYMENT_RECORD_RETENTION_YEARS=5`;
- отдельные токен тестового бота и SQLite-база.

Основные пароли Robokassa для staging не нужны. Приложение не запустится с открытым доступом,
`PAYMENT_MODE=fake`, рабочим режимом Robokassa или пустыми staging-секретами. Штатный deploy допускает
эту конфигурацию, но по-прежнему отклоняет любые реальные списания.

Success URL показывает статическую страницу возврата, сразу пытается открыть Telegram и оставляет
явную кнопку на случай блокировки автоперехода мобильным браузером. Эта страница не подтверждает
оплату. В staging и production выдачу запускает только подписанное паролем №2 серверное уведомление
на `ResultURL`, настроенный в кабинете Robokassa с методом POST. `ResultURL2` не передаётся: для обычной
одноразовой оплаты дополнительный JWS-callback не требуется. Получение, отклонение и принятие
основного callback фиксируются в обезличенном техническом журнале.

Настройки вносятся из PowerShell без записи секретов в командную строку или Git:

```powershell
pwsh -NoProfile -File scripts/configure_staging.ps1 `
  -MerchantLogin your_merchant_login `
  -TestPassword1 (Read-Host "Robokassa test password #1" -AsSecureString) `
  -TestPassword2 (Read-Host "Robokassa test password #2" -AsSecureString) `
  -TelegramId 123456789 `
  -BotUsername money_profile_test_bot
```

Сценарий сохраняет исходный серверный файл как `.env.before-staging` с правами `600`, создаёт
отдельные ключи и базу staging, атомарно обновляет `.env` и проверяет Compose и `Settings` текущего
образа. Он не перезапускает сервис. После его успешного завершения обязательно выполняется единый
штатный деплой из раздела ниже. При ошибке проверки исходный `.env` восстанавливается автоматически.

## Закрытый pilot с боевыми реквизитами

После активации магазина боевые секреты сначала загружаются в закрытую конфигурацию на основе
`.env.pilot.example`:

- `APP_ENV=pilot`;
- `PAYMENT_MODE=robokassa` и `ROBOKASSA_TEST_MODE=false`;
- непустые `ADMIN_TELEGRAM_IDS` и `PILOT_ACCESS_TELEGRAM_IDS`;
- основные пароли Robokassa №1, №2 и №3;
- отдельные токен бота, SQLite-база и ключи шифрования;
- `PAYMENT_PLATFORM_RISK_ACKNOWLEDGED=true`;
- `LIVE_PAYMENTS_ENABLED=false` и `PILOT_LIVE_PAYMENT_REVIEWED=false` при первичной настройке;
- `PAYMENT_CONTACT_RETENTION_DAYS=30` и `PAYMENT_RECORD_RETENTION_YEARS=5`.

Настройка выполняется без передачи секретов в аргументах командной строки или Git:

```powershell
pwsh -NoProfile -File scripts/configure_pilot.ps1 `
  -BotToken (Read-Host "Pilot bot token" -AsSecureString) `
  -MerchantLogin your_merchant_login `
  -Password1 (Read-Host "Robokassa live password #1" -AsSecureString) `
  -Password2 (Read-Host "Robokassa live password #2" -AsSecureString) `
  -Password3 (Read-Host "Robokassa live password #3" -AsSecureString) `
  -TelegramId 123456789 `
  -BotUsername money_profile_pilot_bot `
  -AcknowledgePlatformRisk
```

Сценарий создаёт `.env.before-pilot` с правами `600`, новую базу и новые ключи при первом переходе,
переносит в pilot зафиксированное утверждение методики, атомарно обновляет `.env` и проверяет
конфигурацию текущим образом. Сервис не перезапускается. Следом применяется только
`scripts/deploy.ps1`.

На подготовительном этапе конфигуратор всегда ставит `LIVE_PAYMENTS_ENABLED=false` и
`PILOT_LIVE_PAYMENT_REVIEWED=false`. Кнопка покупки сообщает о паузе, новые боевые счета не создаются,
а загрузка рабочих паролей сама по себе не приводит к списанию. Конкурентный возврат и контроль
фоновой доставки уже усилены, контактные и учётные платёжные данные получили разные сроки, а
локальные резервные копии — расписание и проверку восстановления. Риск отсутствия внешней копии
принят владельцем, существующий канал мониторинга менять не требуется. Pilot всегда остаётся
закрыт allowlist до отдельного подтверждённого перехода в публичный production.

3 сентября 2026 года этот pilot развёрнут на основном боте с доступом только владельца, отдельной
базой и отдельными ключами. Токен и три основных пароля, использованные при первичной настройке через
канал переписки, заменены через безопасный интерактивный ввод. Владелец сообщил о завершённой
проверке юристом и бухгалтером; закрытый контур разрешён для одной реальной операции полного цикла.

В личном кабинете магазина подтверждено активное и одобренное ФНС решение «Робочеки СМЗ». Invoice
API приложения передаёт email и номенклатуру исходного чека, а Refund API — номенклатуру возвратного
чека. Токен pilot-бота и три основных пароля Robokassa заменены 3 сентября 2026 года через
безопасный интерактивный ввод. В тот же день одна закрытая реальная оплата 149 ₽ успешно прошла,
результат и исходный чек были подтверждены владельцем. 4 сентября Robokassa завершила полный
возврат, а владелец подтвердил деньги и возвратный чек в «Мой налог». Создание новых реальных
счетов после операции выключено; полный платёжный и фискальный цикл проверен.

## Публичный production в два этапа

После явного подтверждения [трёх контрольных карт](./golden-cards.md) запрос перехода готовится для
уже развёрнутого точного commit:

```powershell
pwsh -NoProfile -File scripts/request_production_transition.ps1 `
  -AcknowledgeGoldenCards -AcknowledgePublicAccess -AcknowledgePaymentsPaused
pwsh -NoProfile -File scripts/deploy.ps1
```

Запрос принимается только из закрытого pilot с выключенными счетами и полным набором боевых
секретов. Штатный deploy атомарно устанавливает `APP_ENV=production`, очищает pilot-allowlist,
фиксирует `GOLDEN_CARDS_APPROVED=true`, но принудительно оставляет
`LIVE_PAYMENTS_ENABLED=false` и `PRODUCTION_LIVE_PAYMENT_REVIEWED=false`. Поэтому после этого шага
бот доступен всем для бесплатного пути, а кнопка покупки сообщает о паузе и не создаёт счёт.

Перед оплатой вручную проверяются новый пользователь `/start`, согласие, три варианта времени,
бесплатный результат, повторный `/profile`, второй `/start` с другими данными и независимая работа
кнопок обоих профилей, главная страница и `/healthz`. Затем публичные счета могут быть разрешены
отдельным запросом для того же проверенного commit:

```powershell
pwsh -NoProfile -File scripts/request_production_payments.ps1 -State Enable `
  -AcknowledgeProductionSmokeTest -AcknowledgePublicCharge -AcknowledgeEmergencyStop
pwsh -NoProfile -File scripts/deploy.ps1
```

Аварийное отключение выполняется через `-State Disable` и тот же штатный deploy. Оно одновременно
сбрасывает `PRODUCTION_LIVE_PAYMENT_REVIEWED`; новое включение снова требует всех подтверждений.
Запросы привязаны к точному commit, не содержат секретов и не могут быть применены одновременно.
Серверная блокировка также не допускает два параллельных deploy.

4 сентября 2026 года первый этап выполнен: основной бот работает в публичном production,
pilot-allowlist очищен, контрольные карты отмечены подтверждёнными. В тот же день владелец прошёл
бесплатный пользовательский путь и повторный расчёт по другим данным, подтвердил закрытие оставшихся
юридических вопросов профильным юристом и явно разрешил второй этап — включение реальных счетов
отдельным защищённым запросом. Фактические production-флаги хранятся только в закрытом серверном env
и не дублируются в репозитории.

На сервере `195.19.7.56` прямой маршрут до Telegram нестабилен. Поэтому Compose запускает
изолированный SSH/SOCKS-шлюз `telegram-proxy`; только Telegram-сессия бота использует
`TELEGRAM_PROXY_URL=socks5://telegram-proxy:1080`. На шлюзе отдельному пользователю разрешён
форвардинг только к `api.telegram.org:443`. Приватный ключ и `known_hosts` хранятся в
`runtime/ssh`, не попадают в образ или Git и монтируются в proxy-контейнер только для чтения.

## Обновление

Обычное обновление выполняется одной командой из чистого `main` после отдельного коммита:

```powershell
pwsh -NoProfile -File scripts/deploy.ps1
```

Единственное предварительное условие на рабочем компьютере — один раз настроенный SSH-ключ для
`root@195.19.7.56`; сценарий не запрашивает пароль и быстро завершается с понятной ошибкой, если ключ
недоступен.

Другого штатного пути нет. Скрипт отправляет commit в `origin/main`, ждёт появления прошедшего CI образа
с точным SHA, через одно SSH-соединение запускает обновление, делает зашифрованный online-snapshot SQLite,
обновляет `APP_IMAGE` и `SOURCE_COMMIT`, проверяет здоровье контейнера и публичный `/healthz`. Если новая
версия не проходит проверку, скрипт автоматически возвращает предыдущие Compose и образ. Вместе с
релизом он синхронизирует из `.env.example` публичные `LEGAL_DOCS_VERSION`, `OPERATOR_EMAIL` и два
срока хранения платёжных данных, не меняя секреты и режим оплаты серверного `.env`. Устаревший
`PAYMENT_RETENTION_DAYS` удаляется. Неотслеживаемые локальные файлы игнорируются и на сервер не
попадают. Только после успешных health-check и проверки точного запущенного SHA сценарий удаляет
неиспользуемые SHA-образы этого приложения и очищает Docker build cache. Текущий образ определяется
по работающему контейнеру, пропускается явно и дополнительно защищён отсутствием `--force`; ошибка
очистки выдаёт предупреждение, но не откатывает уже проверенный релиз.

CI перед тестами обновляет служебные Python-пакеты и запускает `pip-audit`; известная уязвимость
любой установленной зависимости блокирует сборку образа. Итоговый runtime-образ устанавливает
только зависимости приложения из подготовленных wheel-файлов, после чего удаляет `pip`,
`setuptools` и `wheel` как ненужные в работающем контейнере. CI также проверяет синтаксис штатного
серверного Bash-сценария и всех PowerShell-сценариев до публикации образа.

В репозитории включены Dependabot vulnerability alerts и автоматические security updates.
`.github/dependabot.yml` дополнительно проверяет обновления Python, Docker и GitHub Actions каждый
понедельник; полученный PR не выкладывается автоматически и должен пройти тот же CI и штатный deploy.

В staging, pilot и production `ADMIN_TELEGRAM_IDS` обязателен и является единственным источником
полного административного доступа: каждый ID может смотреть `/stats` и выполнять защищённый
двухшаговый `/refund`. Запись первоначального администратора в SQLite не используется, когда список
задан.

В production новый ID добавляется к существующему списку только запросом для уже развёрнутого
точного commit и следующим штатным deploy; текущие администраторы при добавлении сохраняются:

```powershell
pwsh -NoProfile -File scripts/request_production_admin.ps1 -State Add `
  -TelegramId <telegram_id> -AcknowledgeFullAdminAccess
pwsh -NoProfile -File scripts/deploy.ps1
```

Для отзыва используется `-State Remove`. Запрос не содержит других ID, не выводит текущий список,
не совмещается с изменением состояния оплаты и не позволяет удалить последнего администратора.

Состояние реальных счетов в закрытом pilot запрашивается отдельным безопасным шагом и применяется
только следующим штатным deploy:

```powershell
pwsh -NoProfile -File scripts/request_pilot_payments.ps1 -State Enable `
  -AcknowledgeProfessionalReview -AcknowledgeOwnerOnlyPilot -AcknowledgeRealCharge
pwsh -NoProfile -File scripts/deploy.ps1
```

Для аварийной остановки используется `-State Disable`, после чего немедленно запускается тот же
`scripts/deploy.ps1`. Запрос привязан к текущему commit SHA, не содержит секретов и не переносится на
другую версию. Кандидатная конфигурация проверяется новым образом до переключения контейнера; при
неуспешном обновлении live-pilot откат запрещает создание новых счетов.

`/healthz` возвращает успешный статус только при доступной SQLite, работающем фоновом обработчике
доставки и свежей проверенной резервной копии. Три последовательных сбоя общего цикла доставки
завершают процесс; Compose перезапускает контейнер, а штатный deploy воспринимает нездоровый новый
образ как причину автоматического отката.

Сценарий разрешает публичный тест `APP_ENV=test`/`PAYMENT_MODE=fake`, закрытый staging с тестовой
Robokassa, закрытый pilot с основными реквизитами и guarded production. Live-pilot требует
`PILOT_LIVE_PAYMENT_REVIEWED=true` и ровно один ID, одинаковый в pilot- и admin-списках. Первый
переход pilot → production возможен только по отдельному запросу и всегда оставляет оплату
выключенной. Live-production дополнительно требует `PRODUCTION_LIVE_PAYMENT_REVIEWED=true`,
установленный отдельным запросом после smoke-проверки. Production также требует
`PAYMENT_PLATFORM_RISK_ACKNOWLEDGED=true`; значение хранится только в закрытом серверном env и
документирует решение владельца, а не совместимость с правилами Telegram.
Production-список полных администраторов меняется отдельным запросом для точного commit; кандидатная
конфигурация проверяется до перезапуска, а при ошибке восстанавливается предыдущий список.

После изменения пользовательского пути вручную проверить согласие, fake-открытие результата,
повторный `/profile` и новый расчёт по другим данным без потери доступа к предыдущему профилю; это
продуктовая приёмка, а не альтернативный способ деплоя.

Compose запускает отдельный контейнер `backup`. Он сразу, а затем каждые
`BACKUP_INTERVAL_HOURS=6`, создаёт зашифрованную копию в `/data/backups`, пробует восстановить её во
временный каталог и требует `PRAGMA integrity_check=ok`. Только после этого атомарно обновляется
`/data/backups/status.json`; при ошибке статус становится нездоровым. `BACKUP_MAX_AGE_HOURS=8`
должен быть больше интервала, а локальные файлы удаляются через `BACKUP_RETENTION_DAYS=14`.
Команда ручного восстановления отказывается перезаписывать существующий файл и также проверяет
целостность до публикации результата.

Автоматизация на основном сервере не заменяет внешнюю копию: отказ диска, удаление сервера или
компрометация хоста уничтожит и рабочую БД, и локальный архив. 3 сентября 2026 года владелец явно
решил хранить копии только на основном сервере и принял этот остаточный риск. На немецкий сервер
передаются только обезличенные технические статусы существующего мониторинга; базы и резервные
копии туда не передаются.

По подтверждению владельца на немецком сервере уже настроены мониторинг и Telegram-оповещения;
добавлять новый контур не требуется. Он должен получать только обезличенные счётчики и технические
статусы. Запрещено отправлять туда Telegram ID, данные рождения, email, тексты сообщений, дампы БД,
резервные копии и необработанные exception payloads.

## Откат

Вернуть предыдущий SHA образа. Если новая версия меняла схему, остановить контейнер, восстановить
предмиграционную копию в новый файл через `restore_backup.py`, затем атомарно заменить рабочую БД.
Сценарий восстановления сам требует `PRAGMA integrity_check=ok` и не перезаписывает существующий
файл. Нельзя восстанавливать БД поверх работающего SQLite-файла.

## Миграция отчётности по пути пользователя

При штатном запуске автоматически добавляются `journeys`, `journey_events` и
`orders.analytics_mode`. У старых заказов режим остаётся `unknown`, за исключением явно тестового
провайдера `fake` в отчёте. Состояния старых анкет и подтверждённые факты импортируются с неполной
историей; ручное заполнение нажатий и миграционные команды не нужны. Старые таблицы сохраняются,
поэтому штатный откат образа совместим с этой добавочной миграцией.
Версия документов для описания технического журнала — `2026-09-05.1`; deploy синхронизирует её
штатно из `.env.example`. Правила метрик и хранения описаны в [analytics.md](analytics.md).

## Уведомления об оплатах

Обновление автоматически добавляет таблицу `payment_notifications`; старые платежи не рассылаются.
`PAYMENT_NOTIFICATION_TELEGRAM_IDS` задаёт отдельный список получателей через запятую, пустое
значение выключает отправку. `PAYMENT_NOTIFICATIONS_INCLUDE_TEST=false` исключает тестовые события.
Получатели предварительно открывают бота; `/myid` показывает собственный ID. Получение уведомлений
не выдаёт права статистики или возвратов. В staging/pilot ограничения входа в бот остаются прежними.

После коммита на `main` подготовить конфигурацию для его точного SHA, затем выполнить штатный deploy:

```powershell
pwsh -NoProfile -File scripts/request_payment_notifications.ps1 -TelegramIds "111111,222222"
pwsh -NoProfile -File scripts/deploy.ps1
```

ID в примере условные; список полностью заменяет прежних получателей. Для отключения передать
`-TelegramIds ""`. Для явно запрошенной проверки тестовых событий добавить `-IncludeTest`.
Подготовка записывает только защищённый `.payment-notifications-request` и не меняет работающий
сервис. Сам deploy проверяет SHA, применяет значения в кандидатном env, валидирует настройки,
сохраняет snapshot, обновляет приложение и при ошибке возвращает прежний env. После обработки
запрос удаляется; при неудаче его нужно подготовить заново. Без запроса настройки сохраняются.
Идентификаторы получателей не записываются в GitHub или `.env.example`.

Очередь и журнал хранятся 30 дней. Временные ошибки Telegram повторяются; статус `failed` означает
постоянную ошибку чата, которую нужно устранить у получателя. Код ошибки сохраняется без текста
Telegram-ответа. Подробные гарантии и ограничения доставки описаны в [analytics.md](analytics.md).
